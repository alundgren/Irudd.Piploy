# Self-update's placement relative to the poll loop

**Self-update lives outside `orchestrator.ts`, in the daemon.** `orchestrator.ts` (per [ADR-0002](./0002-module-seams-and-test-split.md)) owns per-application git/docker reconciliation behind an `OrchestratorDeps` interface shaped for that job; self-update fetches a GitHub release asset and swaps `piploy.cjs` — a different concern that doesn't fit that dependency shape.

**Only the automatic timer tick triggers it.** A manual `piploy poll` — whether forwarded to a running daemon or run inline with no daemon reachable — never triggers self-update, only the daemon's internal poll-timer does. When the timer installs an update, the daemon exits and systemd restarts it. A dedicated `piploy self-update` installs an update immediately, then asks the live daemon to stop through its private control socket; systemd again restarts it from the new bundle. This avoids requiring the invoking user to have `systemctl` privileges.

**On each timer tick, self-update runs first and fails open.** If it finds and installs a new version, the daemon exits immediately and that tick's application poll is skipped — normal polling resumes next tick under the new binary. If it finds nothing new, or the check/download itself fails (e.g. GitHub unreachable), the failure is logged and the tick falls through to `orchestrator.poll()` as normal. A self-update hiccup never blocks getting application updates running, mirroring the per-application failure isolation already decided in ADR-0002.

**No dedicated pure decision module.** Unlike `dockerPlan.ts`'s `planImage`/`planContainer` (a real reuse/build/start/recreate state machine), the self-update decision is a one-line comparison of the running version against the latest release tag. A small `shouldSelfUpdate()` function inside `selfUpdate.ts` is enough, unit-tested directly without a separate pure-module file.
